Origin Story

Slide Hasil Meeting Berserakan

“Tiap Selasa ada meeting, tiap minggu saya kerjain task berbeda. Slide hasilnya nyimpen di folder lokal — kadang di email, kadang di WA. Pas mau cari yang lama, susah. Akhirnya kepikiran: kenapa nggak satu tempat aja?” — User, awal Mei 2026

Kondisi Awal

  • 4+ proyek aktif lintas waktu — Domain Archive, Mapping Plan, Calendar, API Phising
  • 65+ task tersebar di banyak konteks
  • Slide tercecer di folder Windows lokal
  • Belum ter-arsip permanen, susah di-share
Tracking pribadi yang sustainable butuh sistem data-driven, bukan folder lokal yang gampang hilang.

Visi Jangka Panjang

Pusat Dokumentasi Mingguan

Setiap proyek, setiap minggu

Domain Archive, Mapping Plan, Calendar, API Phising — semuanya punya slide rapi per Selasa meeting, tertata dalam satu sistem.

Histori lintas waktu

Cari progress 2 bulan lalu? Tinggal scroll. Auto-grouped per Selasa meeting — mengikuti ritme kerja natural.

Single source of truth

Jangka panjang: bisa jadi sumber untuk auto-compile rekap mingguan, bulanan, atau quarterly review.

Shareable by default

Setiap slide punya URL stabil — kirim link, langsung render, tidak perlu attachment file lagi.

Bukan sekadar gallery slide — tapi rekam jejak kerja yang bisa diakses lintas waktu & lintas audience.
02
Masalah

Hambatan Sebelum Sistem Ini

Versi sebelumnya sudah punya halaman /presentations, tapi data-nya hardcoded di kode JavaScript. Tiap tambah deck = edit kode = ribet.

Pain Point Konkret

Empat Masalah Utama

⚙️ Hardcoded Data

Array DECKS di JS — tiap deck baru harus edit kode, push, deploy ulang.

📋 Tidak Ada Admin UI

Belum ada form CRUD — semua operasi presentasi cuma bisa lewat developer experience.

📁 File Tercecer

HTML deck cuma di folder lokal Windows — tidak ada penyimpanan terpusat & reliable.

🔗 Tidak Sinkron dengan Jobs/Tasks

Project list manual hardcoded, tidak konek dengan tabel jobs/tasks yang sudah ada di DB.

Akumulasi friksi kecil membuat user enggan rutin upload slide → akhirnya banyak slide hilang.
Tujuan Proyek

Goals & Constraints

🎯 Goals

  • Data-driven dari DB — tidak ada lagi array hardcoded
  • Upload slide via UI form, otomatis muncul publik
  • Auto-group per Selasa meeting + ISO week label
  • Sinkron dengan tabel jobs & tasks (project tracking existing)

⚠️ Constraints

  • Tetap pakai Supabase Free + Vercel Free (zero cost)
  • Stack existing: React + Vite + Supabase Postgres
  • Akses developer lewat RDP — outbound TCP terbatas
  • Tidak menambah dependency baru di runtime besar

Implementasi

Eksekusi Per-Layer

Empat slide berikutnya menjelajahi detail teknis tiap layer: DB, Storage, Backend Lib, Frontend, dan Edge Proxy.

Layer 1 · Database

Schema, View, dan Relasi

Migration 005 — Tabel presentations

  • Kolom inti: title, meeting_date, status, source, project
  • CHECK constraint: meeting_date harus Selasa
  • RLS policies + trigger updated_at
  • View v_meetings: GROUP BY meeting_date + ISO week label

Migration 006 — Link ke Jobs/Tasks

  • ADD COLUMN job_id FK ke jobs(id)
  • ADD COLUMN task_id FK ke tasks(id)
  • Update status enum: drop Draft, add Pending
  • Default status diubah jadi Proses
View v_meetings = kunci grouping otomatis — frontend tinggal loop, tidak perlu hitung minggu ISO sendiri.

Layer 4 · Frontend

Admin Form + Public Listing

PresentationManager.tsx · /admin

  • Form CRUD dengan validasi (title, project, meeting_date, status)
  • Dropdown PROJECT dari listMyJobs(), grouped by assignee (optgroup)
  • Dropdown TITLE dari listTasksForJob() — nomor urut + status badge
  • Pilih task → title + status auto-fill (mapping: done→Selesai, in_progress→Proses)
  • Toggle: Upload File atau External URL
  • Auto-upload pas submit kalau file belum di-upload

PresentationsPage.tsx · /presentations

  • Header dark theme: indigo #6366f1 + cyan #22d3ee
  • Filter chips per project
  • Loop tiap meeting dari listMeetings()
  • Heading: “Selasa, DD Bulan YYYY — Minggu ke-{iso_week}”
  • Grid 2-3 kolom card per presentasi
  • Card: status pill, title, project pill, deskripsi, link “Buka presentasi →”
Auto-fill title + status hemat klik dan cegah inkonsistensi data entry — operator hampir tidak perlu ngetik manual.
Layer 5 · Vercel Edge Proxy

Proxy /api/deck — Sentuhan Akhir Delivery

Runtime & Logic

  • Runtime: edge (Vercel)
  • Input: query param ?path=presentations/<file>.html
  • Fetch dari supabase.co/storage/v1/object/public/decks/<path>
  • Re-serve dengan Content-Type berdasarkan ekstensi
  • Force text/html; charset=utf-8 untuk .html

Kenapa Wajib

  • Supabase public URL serve .html sebagai text/plain
  • Header bawaan ada CSP sandbox → script Reveal.js diblokir
  • Proxy tidak set CSP sandbox → Reveal.js render normal
  • Caching di Vercel edge → akses kedua lebih cepat
Edge proxy = 1 file kecil, tapi tanpa ini seluruh sistem rusak — slide tampil sebagai source code, bukan presentasi.
Tantangan #1

Hardcoded → Data-Driven UI

❌ Sebelum

  • Array DECKS hardcoded di file JS frontend
  • Tambah deck = edit kode + commit + push + deploy
  • Tidak ada admin UI — operasi cuma untuk developer
  • Slide existing tercecer di folder lokal, susah migrasi

✓ Sesudah

  • Data dari tabel presentations di DB
  • Tambah deck = isi form /admin → submit → muncul publik
  • Admin UI dengan auto-fill, validasi, dan upload terintegrasi
  • Slide existing bisa di-upload via UI tanpa coding
Data-driven UI selalu menang dalam jangka panjang — biaya awal lebih tinggi, tapi maintenance jauh lebih rendah.
Tantangan #2

Content-Type & CSP dari Supabase Storage

❌ Sebelum

  • File .html dari Supabase public URL tampil sebagai source code mentah
  • Content-Type kembali sebagai text/plain
  • Script Reveal.js diblokir oleh CSP sandbox bawaan Supabase
  • Slide tidak render — cuma deretan teks HTML

✓ Sesudah

  • Vercel Edge Function fetch & re-serve dengan Content-Type benar
  • Force text/html; charset=utf-8 untuk file .html
  • Tidak set CSP sandbox → Reveal.js bebas eksekusi
  • Slide render proper dengan navigasi, transisi, fullscreen
Supabase Storage didesain untuk aset statis (PDF/image), bukan HTML interaktif — butuh proxy layer untuk overcome.
Tantangan #3 · Iterative Debug

Tiga Bug Kecil yang Memakan Waktu

#1
Browser auto-detect File.type sebagai text/plain
→ Wrap File ke Blob baru dengan explicit 'text/html; charset=utf-8'
#2
Dropdown PROJECT hardcoded, tidak match jobs real user
→ Sumber dari listMyJobs(), grouped by assignee dengan optgroup
#3
Operator sering lupa klik tombol upload sebelum submit
→ Auto-upload otomatis pas submit kalau file dipilih tapi belum di-upload
Jangan trust File.type dari browser untuk extension-sensitive operations — selalu enforce MIME sendiri.

Pembelajaran

Tiga Insight Utama

🔌 Proxy Layer for HTML

Supabase Storage punya batasan untuk HTML interaktif (Content-Type + CSP). Proxy di edge function adalah pattern reliable untuk overcome.

🗄️ Data-Driven > Hardcoded

UI yang baca dari DB selalu lebih sustainable daripada array hardcoded — investasi awal terbayar berkali-kali.

🎯 Auto-Fill = UX Win

Pilih task → title + status auto-fill. Hemat klik, cegah typo, jaga konsistensi data tanpa beban operator.

Sistem yang dipakai rutin = sistem yang menghilangkan friksi kecil — sekecil apapun, akumulasinya besar.
