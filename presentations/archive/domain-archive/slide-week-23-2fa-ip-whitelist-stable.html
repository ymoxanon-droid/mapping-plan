02
Masalah

Account takeover risk & friction trade-off.

Single password tidak cukup, tapi solusi standar (SMS/email OTP) bawa biaya & friction.

Pain Point

Lima titik lemah sistem keamanan klasik.

Password = satu lapis

Bocor sekali (phishing, database leak, brute force) — game over. Tidak ada lapis cadangan.

SMS 2FA mahal

SMS gateway $0.01–0.05 per pesan × banyak login = biaya operasional terus berjalan.

Email OTP lambat

Inbox delay, spam folder, friction tinggi. User mulai cari cara bypass mental.

Kredensial dipakai bareng

Static credentials tersebar antar device susah di-track. Tidak ada visibilitas siapa login dari mana.

Tidak ada audit trail — kalau ada login mencurigakan dari device asing, tidak ada catatan untuk forensics.
Tujuan Proyek

Goals & Constraints.

Goals

  • 3 lapis defense in depth (password + TOTP + IP)
  • Friction minimal untuk daily use
  • Audit trail lengkap untuk forensics
  • Cost zero — tanpa pihak ketiga berbayar
  • Tanpa SMS gateway atau push provider

Constraints

  • Stack existing: Supabase Auth + React
  • Schema dedicated: datadomain
  • RDP outbound TCP terblok — wajib Management API pattern
  • Tidak boleh maintain infra tambahan
03
Pendekatan

Defense in depth, dengan trigger pintar.

3 lapis pertahanan yang aktif kondisional — bukan blanket enforcement.

Arsitektur

Tiga lapis defense in depth.

L1
Password (Supabase Auth)
Email + password normal lewat Supabase Auth. Hash di Postgres, standar industri.
Always-on
L2
Master TOTP (custom shared secret)
otplib generate 6-digit OTP rolling 30 detik. Secret di-store di datadomain.master_totp.
Conditional
L3
IP Whitelist (per-user)
Tabel user_ip_whitelist dengan status pending / approved / rejected — di-approve admin.
Trust gate
3 lapis yang saling melengkapi: password (apa yang kamu tahu) + TOTP (apa yang kamu punya) + IP (dari mana kamu).
Smart Trigger

OTP cuma muncul kalau IP belum whitelist.

✓ Device sehari-hari (IP whitelisted)

1.Email + password
2.IP dicek → sudah whitelisted
3.MFA challenge di-skip
Langsung masuk · 1 klik

⚠ Device baru (IP belum dikenal)

1.Email + password
2.IP dicek → unknown
3.Request whitelist + minta OTP
Verifikasi penuh · approval admin
Friction conditional jauh lebih palatable daripada friction selalu. Itu kunci adopsi.
04
Implementasi

Eksekusi per lapis.

Database, backend logic, dan UI — dengan smart trigger jadi simpul utama.

Layer Database

Schema datadomain · tabel & constraint.

Tabel

  • master_totp — user_id, secret, created_at
  • user_ip_whitelist — id, user_id, ip, status, requested_at, approved_at, approved_by, reason
  • Status enum: pending · approved · rejected

RPC & Constraint

  • fn_request_ip_whitelist
  • fn_approve_ip_whitelist
  • fn_reject_ip_whitelist
  • RLS policies + GRANT level tabel ke authenticated
  • Partial unique idx: UNIQUE (user_id, ip) WHERE status='pending'
Partial unique index (week 23 fix) — supaya approve ulang setelah rejected tidak bentrok dengan history.
Layer Backend

Library di src/lib/ · logic per-lapis.

mfa.ts

Verifikasi TOTP via otplib. Window toleransi 1 step (30 detik) untuk drift jam.

ipGate.ts

Cek IP user terhadap whitelist. Return status: trusted / pending / unknown.

realtime sub

Postgres CDC ke admin panel — pending requests muncul real-time tanpa polling.

Library kecil & fokus per concern — bisa di-unit-test independen tanpa setup UI.
Layer UI/UX

Form login adaptif + admin panel realtime.

User-facing

  • Login form normal (email + password)
  • Conditional MFA challenge (cuma jika IP belum whitelist)
  • Request whitelist screen + status badge (pending / approved / rejected)
  • MFA verified flag di localStorage per-user · TTL 8 jam

Admin-facing

  • Daftar pending requests (realtime, no refresh)
  • Tombol approve / reject + reason
  • History & audit log per user
  • Notif push browser saat request baru masuk
UX adaptif — user device biasa nyaris tidak merasakan ada security tambahan.
Tantangan #1 · Adopsi

Friction = musuh adopsi.

Sebelum (Week 22)

  • OTP wajib di setiap login
  • User mulai cari bypass mental
  • Frustrasi naik tiap hari
  • Risiko: user nonaktifkan 2FA diam-diam

Sesudah (Week 23)

  • OTP conditional — cuma kalau IP belum whitelist
  • Daily use: 1 klik, no friction
  • Device baru: tetap aman dengan full check
  • Adopsi smooth — security stays on
Smart trigger menang dari blanket enforcement. Security yang dibypass = security yang tidak ada.
Tantangan #2 · Realtime

Stale closure di useEffect subscription.

Bug halus

  • useEffect capture user.id dari render saat itu
  • Logout → login lain → subscription masih pakai user.id lama
  • Admin lihat pending requests user salah
  • Susah reproduce, intermittent

Solusi

  • useRef untuk pegang user.id current value
  • Dependency array dibenarkan
  • Subscription resubscribe saat user berubah
  • Realtime correctly scoped per-user
Realtime subscription harus closure-aware. useRef pattern wajib untuk state yang berubah di luar render.

Pelajaran & Arah

Insight utama dan satu fokus ke depan.

Pelajaran #1 · Friction = musuh adopsi

Security yang terlalu intrusive bakal dibypass. OTP conditional menang dari OTP selalu. Smart trigger > blanket enforcement.

Pelajaran #2 · Realtime + React closure

useEffect subscription harus closure-aware. useRef pattern wajib — kalau tidak, stale state akan kena bug intermittent yang susah debug.
