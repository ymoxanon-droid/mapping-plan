02
Masalah

Risiko Sistem Lama

Sebelum proyek ini, dashboard hanya dilindungi satu lapis — kombinasi username/password.

Masalah Utama

Single Point of Failure

🔓 Tidak ada layer kedua

Kalau password bocor (phishing, keylogger, leak), penyerang langsung dapat akses penuh ke dashboard. Tidak ada hambatan tambahan.

🌐 IP tidak dibatasi

Siapa pun dari IP mana pun di dunia bisa mencoba login kalau punya kredensial. Tidak ada kontrol berbasis lokasi.

📋 Tidak ada audit visual

Tidak ada notifikasi kalau ada akses dari IP tidak dikenal. Pelanggaran baru ketahuan saat data sudah hilang.

⚙️ Tidak ada recovery

Kalau perangkat MFA hilang, tidak ada flow untuk recovery yang aman tanpa melibatkan reset penuh.

Kebutuhan: minimum 2 layer otentikasi + kontrol IP + jalur recovery aman.
Tujuan Proyek

Goal & Constraint

🎯 Goals

  • Two-Factor Authentication via TOTP (Google Authenticator)
  • Per-user IP whitelist (multi-entry, CIDR support)
  • Bypass flow saat IP berubah (recovery via email link)
  • Admin approval untuk IP baru (kontrol manual)
  • Audit trail siapa approve apa & kapan

⚠️ Constraints

  • Biaya: 0 — pakai Supabase Free + Vercel Free tier
  • Compatible dengan stack existing (React + Supabase)
  • Anti-lockout: opt-in mode, watchdog timeout
  • Workable di RDP dengan outbound TCP block
  • Tidak boleh ada flash dashboard ke gate UI

Arsitektur Solusi

Tiga lapis pertahanan berlapis (defense-in-depth) — masing-masing lapis berdiri sendiri.

Three-Layer Defense

Setiap Login Melewati 3 Pemeriksaan

Layer 1 · Password
Username + password lewat Supabase Auth. Lockout: 5 percobaan gagal = 15 menit cooldown.
existing
Layer 2 · TOTP (2FA)
Kode 6-digit dari Google Authenticator / Authy. Verified server-side oleh Supabase Auth MFA.
baru
Layer 3 · IP Whitelist
Cek IP klien (dari header Cloudflare) terhadap CIDR yang terdaftar. IP baru → minta approval admin.
baru
Penyerang harus tembus semua 3 lapis sekaligus untuk dapat akses. Bocornya satu lapis tidak cukup.

04
Implementasi

Eksekusi Sistem

Dari skema database hingga UI — dibangun secara bertahap & teruji end-to-end.

Database Layer

Skema & Logika Bisnis

3 Tabel Inti

  • admin_ip_whitelist — daftar IP/CIDR per user
  • ip_bypass_tokens — token sekali pakai (SHA-256 hash)
  • ip_bypass_requests — pending approval queue

Row-Level Security aktif di semua tabel.
User hanya bisa lihat datanya sendiri.

12 RPC Functions

  • ip_in_whitelist — cek CIDR match
  • request_ip_bypass — generate token
  • verify_ip_bypass — konsumsi token, buat pending
  • approve_bypass_request — admin approve
  • reject_bypass_request — admin reject
  • count_pending_bypass_requests — untuk badge
Semua logika kritis ada di DB sebagai RPC (SECURITY DEFINER). Frontend tidak bisa nge-bypass dengan curl.
Edge Functions

3 Endpoint Serverless

POST

check-access

Setelah login, validasi IP klien (dari header cf-connecting-ip) terhadap whitelist user.

POST

send-ip-bypass

Saat user request bypass, generate token + kirim email link via Resend. Rate-limit 3/30 menit.

POST

verify-ip-bypass

Saat user klik link, validasi token + bikin pending request (IP baru tidak auto-add).

IP klien dibaca server-side dari header CDN — tidak bisa di-spoof oleh frontend.
Frontend Components

5 Komponen Baru, 1 Halaman Baru

Untuk End User

  • MfaChallenge — input kode 6-digit setelah password
  • MfaEnrollment — setup TOTP dengan QR code
  • IpGate — full-screen kalau IP belum diizinkan
  • IpBypassPage — halaman landing dari email link

Untuk Super Admin

  • IpWhitelistManager — CRUD IP + pending requests
  • Tab "Security (2FA + IP)" di Admin Panel

Tantangan

Hambatan & Solusi

Setiap proyek nyata punya kejutan teknis. Tiga tantangan terbesar yang kami selesaikan.

Tantangan #1

Network Restriction di RDP

❌ Masalah

  • RDP server memblokir outbound TCP non-HTTPS
  • Supabase CLI db push butuh koneksi langsung ke port 5432 → gagal
  • Supabase CLI functions deploy bypass env HTTPS_PROXY → gagal
  • DBeaver harus pakai SOCKS bridge (gost)

✓ Solusi

  • Custom script apply-migration-via-pat.ts
  • Custom script deploy-function-via-pat.ts
  • Pakai Supabase Management API (HTTPS:443)
  • Routing via HTTP proxy 8803 (undici ProxyAgent)
  • Inline shared utilities ke setiap edge function
Hambatan infrastruktur sering tidak terprediksi. Bikin tooling sendiri kadang lebih cepat dari fight CLI vendor.
Tantangan #2

Iterative Database Debugging

040
RLS aktif tapi user dapat "permission denied"
→ GRANT level tabel masih harus eksplisit, RLS saja tidak cukup
041
Function STABLE tapi ada UPDATE statement → error 0A000
→ Drop keyword STABLE, jadikan VOLATILE
042
pgcrypto functions tidak reachable
→ Qualify dengan extensions.digest() + tambah ke search_path
043
Column "email" ambiguous → error 42702
→ Qualify dengan alias tabel: admin_access.email
045
Column "status" ambiguous (output column vs table)
→ Pakai alias r.status di WHERE clause
5 migration fix berturut-turut — sistem stabil setelah iterasi cepat dengan diagnostic script.
Tantangan #3

UX: Hilangkan Kedip & Flash

❌ Sebelum

  • Setiap refresh, dashboard tampil sebentar → IpGate muncul
  • Setiap refresh, "Memverifikasi akses..." muncul walau user sudah lolos
  • UX terasa lag & tidak profesional
  • Distraksi visual setiap navigasi

✓ Sesudah

  • localStorage flag: _ip_check_passed + _mfa_check_passed
  • Optimistic render: kalau pernah lolos → langsung tampil dashboard
  • Background re-check tetap jalan, kalau gagal → IpGate cover
  • Flag di-clear saat logout / state berubah ke blocked
  • Refresh = mulus, tanpa flicker
UX detail kecil membedakan "kerja" dan "kerja profesional". Pessimistic loading screen tidak selalu jawaban terbaik.

Pembelajaran

Insight Teknis & Operasional

🔐 Security

RLS tidak menggantikan GRANT. Defense-in-depth = setiap lapis independen — jangan asumsikan satu lapis pasti aktif.

🧪 Diagnostic First

Tooling untuk reproduce bug (RPC direct call, network inspector) jauh lebih cepat dari guesswork — apalagi saat iterasi.

🎯 UX = Detail

Optimistic UI + localStorage flag = perbedaan antara "berfungsi" dan "profesional". Worth the extra code.

Project ini memvalidasi pendekatan: build small, test continuously, fix iteratively, document everything.
