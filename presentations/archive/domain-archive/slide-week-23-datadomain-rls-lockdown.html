02
Masalah

Breach LIVE — terbuka sekarang

RLS ternyata dimatikan di mayoritas tabel (policy ada tapi inert), ditambah blanket GRANT ... TO anon. Hasilnya: publik bisa baca data sensitif tanpa login.

Temuan

4 lubang nyata

🔑 API key kebaca publik

Tabel settings punya anon SELECT + RLS off → kunci Ahrefs/Moz/dll terbuka.

🌐 Data jutaan baris

anon bisa baca scan_access_codes, scan_sessions, ~6jt baris ahrefs, daftar admin.

🚫 RLS dimatikan

29 dari 42 tabel rls_enabled=false → policy yang ada jadi sia-sia.

💣 Eskalasi privilege

Policy admin_access_update USING(true) → siapa pun login bisa angkat diri jadi super_admin.

Lapisan auth (Master TOTP + IP whitelist) tidak jebol — yang jebol = kerahasiaan data & kontrol tulis di level DB.
Tujuan

Goal & Constraint

🎯 Goals

  • anon (publik) tidak bisa baca/tulis data
  • Akses tidak melewati cek role aplikasi
  • App admin tetap jalan normal
  • Ada jalur rollback yang aman

⚠️ Constraints

  • DB production, dipakai live — tak boleh down
  • 2 fungsi pre-login wajib tetap anon
  • RLS tak bisa dites via PAT (jalan as owner → bypass)
  • Akses via RDP: CLI standar diblok, lewat proxy
Aturan emas: policy dulu → ENABLE RLS → REVOKE anon — jangan pernah ENABLE tanpa policy (= app langsung error).

Satu migration idempotent (053): bikin policy berbasis keanggotaan admin di setiap tabel, nyalakan RLS, lalu cabut akses anon — sisakan hanya yang dibutuhkan login.

Implementasi

Eksekusi yang aman

Recon baseline → tulis migration + rollback → verifikasi adversarial → apply ke production → verifikasi ulang.

Migration 053

Inti perubahan

Helper keanggotaan

  • is_admin_member() — anggota aktif via user_id atau email JWT
  • is_super_admin() diperkuat: tambah fallback email
  • Keduanya SECURITY DEFINER, anti-rekursi RLS

Policy & RLS

  • 33 tabel data → 1 policy FOR ALL member
  • settings/admin_access diperketat (super_admin)
  • Drop policy admin_access_update USING(true)
  • ENABLE RLS di semua tabel sensitif
Kabar baik: policy lama sebagian besar sudah benar — masalah utamanya RLS yang dimatikan. Jadi lebih banyak "nyalain & rapikan" daripada nulis dari nol.
Cabut Anon

Yang dicabut vs disisakan

REVOKE ALL ON ALL TABLES IN SCHEMA datadomain FROM anon;
REVOKE EXECUTE ON ALL FUNCTIONS IN SCHEMA datadomain FROM anon;

-- sisakan HANYA yang dibutuhkan SEBELUM login (semua SECURITY DEFINER):
GRANT INSERT ON datadomain.admin_audit_log TO anon; -- log gagal-login
GRANT EXECUTE ON lookup_admin_email_by_username(text) TO anon;
GRANT EXECUTE ON check_login_lockout(text) TO anon;
GRANT EXECUTE ON verify_ip_bypass(text,text,text) TO anon;
Cuma cabut dari anon — grant authenticated dibiarkan utuh. 3 fungsi sisa tak menyentuh tabel langsung (definer), jadi login tetap jalan.
Tantangan #1

Nyalakan RLS tanpa mematahkan login

❌ Risiko

  • Login butuh anon SEBELUM authenticated (cari username, cek lockout)
  • Cabut anon asal-asalan → tak ada yang bisa login
  • Member-scan ternyata anon murni (signInAnonymously = no-op)

✓ Solusi

  • 3 fungsi pre-login dibuat SECURITY DEFINER → tetap dipanggil anon
  • anon disisakan persis 4 akses, sisanya dicabut
  • Member-scan via kode = mati by design (keputusan: wajib login)
Memetakan apa yang dipanggil anon pre-login dari kode app dulu = kunci agar revoke tidak memutus login.
Tantangan #2

Verifikasi adversarial (5 agen)

01
RLS ternyata OFF, bukan cuma grant
→ recon read-only, simpan baseline lengkap
02
Blocker: is_super_admin tanpa fallback email
→ bisa deadlock bootstrap → ditambah fallback email
03
3 "blocker" lain dari reviewer
→ ditelaah = false positive (salah baca anon↔authenticated)
04
Tes RLS via PAT menyesatkan (bypass as owner)
→ verifikasi nyata lewat app + login per role
Workflow multi-agen menangkap 1 blocker asli & menyaring 3 alarm palsu — diperbaiki sebelum menyentuh production.

Pembelajaran

Insight Teknis

🚫 RLS ≠ GRANT

RLS yang dimatikan bikin policy inert — grant saja tak cukup menjaga data.

🧪 PAT bypass RLS

Tes via superuser menyesatkan ("aman" palsu). Verifikasi wajib via app + login.

🪪 Email fallback

Cocokkan keanggotaan via email JWT, bukan cuma user_id (sering belum sinkron).

Connection string role pribadi cocok untuk DBeaver/tooling — bukan ditaruh di kode app browser (malah membocorkan password DB).
