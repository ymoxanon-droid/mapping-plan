02
Masalah

Empat tembok sekaligus

Bukan satu bug — tapi rentetan hambatan dari operasional sampai keterbatasan infrastruktur.

Pain Points

Kenapa backup belum jalan

🔁 Gagal tiap hari

Cron menyala tapi selalu gagal → spam email kegagalan ke inbox setiap pagi.

🧩 Setup tak kelar

Tujuan penyimpanan & 5+ secret tak pernah disiapkan — pipeline berhenti di tengah jalan.

📦 Data kegedean

Dump ~174 MB/hari (terkompresi). Banyak storage gratis tak sanggup menampung ukuran & retensi-nya.

🔒 RDP blok DB

Outbound TCP (port 5432/6543) diblok → dump/tes tak bisa dijalankan dari komputer lokal.

Tanpa diberesin: data prod 3,15 GB cuma bergantung pada satu vendor, tanpa cadangan off-site yang teruji.
Tujuan Proyek

Goal & Constraint

🎯 Goals

  • Backup harian otomatis (set & forget)
  • Terenkripsi end-to-end (AES-256)
  • Off-site — beda vendor dari DB prod
  • Bisa di-restore & benar-benar teruji
  • Gratis / nyaris nol biaya

⚠️ Constraints

  • RDP blok TCP keluar → tes via CI, bukan lokal
  • Dataset besar (174 MB/hari, terus tumbuh)
  • Tanpa nambah dependency berat / SDK baru
  • gh CLI tak tersedia di mesin
  • Tak boleh mengganggu branch kerja lain

04
Implementasi

Eksekusi & tantangan

Empat percobaan run sebelum hijau — tiap kegagalan menyingkap kendala baru yang lebih dalam.

Detail Teknis

Dua komponen kunci

🌊 Dump streaming (hemat memori)

  • Baca 1 SELECT per tabel, tulis SQL bertahap ke gzip stream
  • Teks semua-tabel tak ditumpuk di memori
  • NODE_OPTIONS=--max-old-space-size=4096 + timeout 20m
  • Memori puncak ≈ 1 tabel, bukan seluruh DB

☁️ Upload Drive (REST, tanpa SDK)

  • OAuth2 refresh-token → access token
  • Resumable upload (wajib utk file besar)
  • Folder "Database Backups" dibuat otomatis
  • Prune file > 30 hari · scope minimal drive.file
Enkripsi AES-256-GCM dipertahankan sama di semua versi → backup lama tetap kompatibel saat restore.
Tantangan #1 · Tujuan Penyimpanan

Supabase Free → Google Drive

❌ Supabase Free (gagal)

  • Storage cuma 1 GB · limit file 50 MB
  • Upload 174 MB ditolak → EntityTooLarge
  • 30 hari × 174 MB ≈ 5 GB → tak muat
  • Vendor sama dengan DB prod (bukan off-site sejati)

✓ Google Drive (jalan)

  • 15 GB gratis · tanpa limit file 50 MB
  • 174 MB/hari, ~5 GB/30 hari → muat lega
  • Pakai akun Gmail yang sudah ada (0 biaya)
  • Off-site — beda vendor dari Supabase ✅
Ukuran data nyata (3,15 GB DB) baru ketahuan saat dump pertama berhasil — memaksa pivot tujuan ke storage yang lebih lega & benar-benar off-site.

Keamanan & Isolasi

Aman walau berbagi repo

🔐 Enkripsi at-rest

AES-256-GCM, salt + iv acak per file. File yang dicuri pun tak terbaca tanpa passphrase.

🛡️ Repo guard

if: github.repository == ... — cron menyala di 2 repo tapi job hanya jalan di repo user (yang punya secret).

🔑 Secret minimal

5 secret di GitHub, scope OAuth paling sempit (drive.file — hanya file buatan app).

Repo di-push ke dua remote (user & atasan), tapi backup hanya berjalan di satu — file identik, tetap pub-safe, tanpa spam di repo atasan.

Pembelajaran

Insight Teknis & Operasional

🧠 Rasa aman palsu

Backup gagal ≠ DB rusak — tapi backup yang "belum kelar" lebih bahaya: terlihat ada, padahal tak berfungsi.

🌊 Streaming > muat-semua

Dataset besar tak boleh diserap ke RAM sekaligus. Streaming bertahap = memori stabil, tahan pertumbuhan data.

🌍 Off-site itu wajib

Backup di vendor yang sama = satu titik kegagalan. Cadangan beda vendor adalah inti disaster recovery.

RDP yang memblok DB justru memaksa arsitektur lebih sehat: backup berjalan di CI, bukan di mesin rapuh seseorang.
