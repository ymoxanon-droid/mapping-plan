02
Masalah

Risiko Sebelum Minggu Ini

Sistem lama hanya punya 1 lapis pertahanan — tidak ada strategi untuk skenario password leak atau akses dari lokasi mencurigakan.

Masalah Utama

Single Point of Failure

🔓 Tidak ada lapis kedua

Password bocor (phishing, keylogger, leak) → penyerang langsung dapat akses penuh dashboard.

🌐 IP tidak dibatasi

Siapa pun dari IP mana pun di dunia bisa coba login. Tidak ada kontrol berbasis lokasi.

⚠️ Sesi tidak bisa di-kick manual

Kalau ada login mencurigakan, admin tidak punya cara cepat invalidate sesi user tertentu.

⚙️ Tidak ada recovery aman

Kalau perangkat 2FA hilang atau IP berubah, tidak ada flow recovery dengan approval ter-audit.

Kebutuhan: 2FA + IP whitelist + admin approval flow + emergency kick session.
Tujuan Proyek

Goal & Constraint

🎯 Goals

  • Two-Factor Authentication custom (1 master secret, terpusat di roket)
  • Per-user IP whitelist server-side
  • Admin approval untuk request IP baru
  • Force logout user (manual & otomatis dari kebijakan)
  • Audit trail keputusan approve/reject
  • Trade-off cerdas: skip OTP kalau IP sudah whitelist (UX)

⚠️ Constraints

  • Biaya: 0 — Supabase Free + Vercel Free
  • Stack existing: React + Vite + Supabase Postgres + Edge Functions
  • RDP development outbound TCP diblok (kecuali HTTP proxy)
  • Anti-lockout: opt-in mode + watchdog timeout
  • Tidak boleh ada flash dashboard ke gate UI

Pendekatan

Arsitektur Sistem

3 lapis pertahanan independen + custom Master TOTP yang terpusat di admin tertinggi.

Three-Layer Defense

Setiap Login Melewati 3 Pemeriksaan

Layer 1 · Password + Lockout
Supabase Auth standard. 5 percobaan gagal = 15 menit cooldown. Existing dari sprint sebelumnya.
existing
Layer 2 · Master TOTP (Custom)
1 shared secret. Hanya roket@admin punya QR/Authenticator. User lain dapat kode via chat. Cuma muncul saat IP belum whitelist.
baru
Layer 3 · IP Whitelist Server-Side
Cek IP dari header Cloudflare (cf-connecting-ip). Wajib untuk semua admin. IP baru → IpGate + approval admin.
baru
Hacker yang tembus 1 lapis (mis. password) tetap ke-block di lapis lain. Defense-in-depth real.

Implementasi

Eksekusi Teknis

DB schema + Edge Functions + Frontend components + Admin tools. Dibangun bertahap & teruji end-to-end.

Database Layer

Skema & Business Logic

5 Tabel Inti

  • admin_ip_whitelist — CIDR per user
  • ip_bypass_tokens — token sekali pakai (SHA-256)
  • ip_bypass_requests — pending approval queue
  • master_totp — secret terpusat (1 row enabled)
  • admin_access — role hierarchy (existing)

15+ RPC Functions

  • ip_in_whitelist, should_enforce_ip
  • request_ip_bypass, verify_ip_bypass
  • approve_bypass_request, reject_bypass_request
  • list_all_admin_ips, remove_user_ip (super admin)
  • force_logout_user (manual kick)
  • has_master_totp, set_master_totp, disable_master_totp
Semua logika kritis di DB sebagai RPC SECURITY DEFINER. Frontend tidak bisa bypass dengan curl.
Edge Functions

4 Endpoint Serverless

POST

check-access

Validasi IP klien dari header cf-connecting-ip + multi-fallback header. Polling 60 detik.

POST

send-ip-bypass

Generate token + kirim email link via Resend. Rate-limit 3/30 menit. Dev_link fallback.

POST

verify-ip-bypass

Konsumsi token + bikin pending request (BUKAN auto-add). IP server-side via header.

POST

verify-master-totp

Implementasi TOTP RFC 6238 (HMAC-SHA1, ±30s window). Self-contained.

Edge function self-contained — Management API tidak bundle deps seperti CLI eszip.

05
Tantangan

Hambatan & Solusi

3 tantangan terbesar yang kami selesaikan iteratively dalam sprint ini.

Tantangan #1

RDP Network Restriction

❌ Masalah

  • Outbound TCP non-HTTPS diblok di RDP
  • Supabase CLI db push butuh port 5432 langsung
  • Supabase CLI functions deploy bypass HTTPS_PROXY
  • Tidak bisa update DB schema atau deploy fungsi

✓ Solusi

  • Custom apply-migration-via-pat.ts
  • Custom deploy-function-via-pat.ts
  • Routing via HTTP proxy 127.0.0.1:8803
  • Inline semua shared imports di edge function
  • Self-contained TOTP implementation di Deno
Pakai Supabase Management API (HTTPS:443) + undici ProxyAgent = bypass semua restriction.
Tantangan #2

Iterative Database Debugging (13+ Migration)

040
Permission denied padahal RLS aktif
→ RLS != GRANT. Tambah GRANT level tabel eksplisit
041
UPDATE di function STABLE → error 0A000
→ Drop keyword STABLE, default VOLATILE untuk DML
042
pgcrypto functions tidak reachable
→ Qualify extensions.digest() + tambah ke search_path
043/045/050/051
Column ambiguous: email, status, user_id
→ Alias tabel eksplisit (a.email, r.status, dst)
052
Approve gagal: UNIQUE constraint violated
→ Partial unique index untuk status='pending' saja
Tooling diagnostic (test-rpc.cjs) bikin debug iterasi cepat — total 4 jam untuk 5 fix.
Tantangan #3

UX & Policy Iteration

❌ Iterasi awal

  • Dashboard flash sebentar saat refresh → IpGate muncul
  • "Verifikasi akses..." muncul tiap kali walau lolos
  • OTP wajib semua user (admin & non-admin)
  • OTP muncul DUA KALI di flow IP blocked
  • MFA flag hilang setiap reload tab

✓ Iterasi akhir

  • localStorage flag: optimistic skip loading
  • localStorage _mfa_verified_at dengan TTL 8 jam
  • OTP HANYA kalau IP belum whitelist (skip kalau whitelist)
  • 1 OTP saja di IpGate (di-step internal sebelum bypass)
  • Realtime via Supabase channel + polling 15s backup
UX-driven iteration: simpler beats complex. Trade-off security-vs-UX dilakukan eksplisit by user.

Pembelajaran

Insight Teknis & Operasional

🔐 Defense in Depth

3 lapis pertahanan independen. Bocornya 1 lapis tidak cukup untuk bobol — itu definisi defense-in-depth real.

🧪 Diagnostic Tooling

Bikin script test-rpc.cjs untuk reproduce bug = debug 10x lebih cepat dibanding tebakan.

🎯 UX-Driven Policy

Final policy "OTP only when IP blocked" = trade-off user. Simpler & less friction tetap aman karena lapis 3 robust.

Proyek ini memvalidasi: build small + test continuously + adjust to feedback = sistem yang fit purpose.
